# Metric schema

This page is the contract for metrics authored by Gosoline. The canonical names, instrument types, authored units, dimensions, and descriptions below describe what the emitters actually record; they are not a copy of OpenTelemetry's metric inventory. Gosoline follows OpenTelemetry semantic conventions for metric grammar, units, and attribute shape where useful, but emits its own names. For example, `http.server.request.duration` is authored by Gosoline and exported by OTEL as `gosoline.http.server.request.duration`, not as an unqualified semantic-convention metric.

**Source status:** The duration histogram profiles and metric-v2 contract below are implemented in the Gosoline SDK source pinned for this migration, [`v0.68.4-0.20261105105331-d2be354ca7bc`](https://github.com/justtrackio/gosoline/commit/d2be354ca7bc975f6e7a33c6d2cbdec1330feb7d). Its canonical [metric semantic conventions](https://github.com/justtrackio/gosoline/blob/d2be354ca7bc975f6e7a33c6d2cbdec1330feb7d/pkg/metric/SEMCONV.md) describe Gosoline's metric grammar, units, and attribute shape. The standalone HTTPServer source pinned here, [`v0.6.5-0.20261110113715-f6493110894a`](https://github.com/gosoline-project/httpserver/commit/f6493110894a10167e364d742dd543759197cb10), remains a pre-release pseudo-version from an open provider change; it is not a stable HTTPServer release. Its source describes the CloudWatch rejection projection below; see the [Gosoline SDK HTTP server reference](/docs/pr-11/reference/package-gosoline-httpserver/.md) and [standalone HTTP server reference](/docs/pr-11/reference/package-httpserver/.md). These statements describe source, not application adoption or deployment.

## Schema version[​](#schema-version "Direct link to Schema version")

The current metric contract is **`v2.0`** (`metric.SchemaVersion`). When the metric daemon is enabled, Gosoline publishes that value as metadata under `metric.schema_version`. Removing or renaming an authored metric name, dimension key, or unit representation is a breaking change; purely additive metric changes are minor. The current V2 release is the single migration from V1 and emits no dual versions. A new build's schema version does not automatically migrate dashboards, alerts, queries, or autoscaling policies.

## Authored names and writer output[​](#authored-names-and-writer-output "Direct link to Authored names and writer output")

A Gosoline metric is authored as a canonical namespace and leaf, joined with a dot—for example, `http.server` + `request.duration` becomes `http.server.request.duration`. The namespace identifies the emitting subsystem; it is not the application identity. A namespace-less application metric instead uses its leaf as its complete authored name.

Each writer renders that canonical name for its backend:

| Authored metric                           | CloudWatch metric name      | Prometheus metric name                          | OTEL metric name                        |
| ----------------------------------------- | --------------------------- | ----------------------------------------------- | --------------------------------------- |
| `http.server.request.duration`            | `HttpServerRequestDuration` | `gosoline_http_server_request_duration_seconds` | `gosoline.http.server.request.duration` |
| `http.server.requests`                    | `HttpServerRequests`        | `gosoline_http_server_requests_total`           | `gosoline.http.server.requests`         |
| `http.server.routed.requests`             | `HttpServerRoutedRequests`  | `gosoline_http_server_routed_requests_total`    | `gosoline.http.server.routed.requests`  |
| `http.server.responses`                   | `HttpServerResponses`       | `gosoline_http_server_responses_total`          | `gosoline.http.server.responses`        |
| `http.server.routed.responses`            | `HttpServerRoutedResponses` | `gosoline_http_server_routed_responses_total`   | `gosoline.http.server.routed.responses` |
| Namespace-less counter `my.custom.metric` | `MyCustomMetric`            | `gosoline_my_custom_metric_total`               | `my.custom.metric`                      |

The first row's duration is authored in milliseconds; Prometheus and OTEL values are scaled to seconds, and both names show the seconds base unit. The Prometheus histogram exposition adds its normal sample suffixes to the base name. Prometheus dimension keys also replace dots with underscores, so the HTTP `request.method`, `route`, and `response.status_code` attributes become `request_method`, `route`, and `response_status_code` labels. The default-dimension marker `{{default}}` is rendered as an empty Prometheus label value. Metric writers export emitted measurements; they do not synthesize samples from a registry of registered metric defaults. A missing series means no sample has been observed for that metric and attribute set, not that its value is zero. A zero is present only when an emitter records an actual zero-valued measurement. When migrating code that relied on registered definitions, supply metadata on each emitted metric (including its instrument kind, unit, and priority) rather than expecting a registry match to fill it in. `NewWriter(namespace string)` takes only the writer namespace; it does not accept or register a metric inventory. The namespace controls naming, not which metrics exist.

For Gosoline metrics, the Prometheus writer always uses the fixed `gosoline` prefix. It names the framework that authored the metric, not the application. Do not configure an application-specific Prometheus prefix: `metric.writer_settings.prometheus.naming.namespace_pattern` and `metric.writer_settings.prometheus.naming.namespace_delimiter` no longer control metric names. Put application identity on the scrape target through service discovery/target labels; Gosoline does not copy app identity into each metric name.

CloudWatch keeps its separate, still-supported namespace setting:

```
metric:

  writer_settings:

    cloudwatch:

      naming:

        namespace_pattern: "{app.namespace}-{app.name}"

        namespace_delimiter: "/"
```

This setting controls the CloudWatch **namespace** in AWS, not the metric name. CloudWatch metric names are rendered from the authored namespace and leaf as one PascalCased name; it does not add `gosoline` to the metric name. The datum's metric namespace and the CloudWatch service namespace are separate concepts. Consequently, writing an application-authored metric with an empty Gosoline namespace does not remove the configured CloudWatch namespace: only its metric name is PascalCased from the leaf.

For a namespace-less custom name, CloudWatch converts canonical separators in the leaf too: `my.custom.metric` becomes `MyCustomMetric`. Prometheus still applies its fixed `gosoline` writer prefix, converts dots in the leaf to underscores, and appends the unit/counter suffix (the example is a counter). OTEL normalizes and exports that namespace-less leaf without a `gosoline.` prefix. These behaviors are intentional; re-key CloudWatch dashboards or alarms using namespace-less custom metrics if they previously depended on the unrendered dotted leaf.

## Units and descriptions[​](#units-and-descriptions "Direct link to Units and descriptions")

The inventory's unit is the unit the emitter authors. Gosoline durations are generally recorded in milliseconds, and Prometheus and OTEL scale those values to seconds and render the base-unit suffix or instrument unit. `cloud.aws.kinesis.acquire.duration` is the one duration authored in seconds. Byte histograms are authored in bytes. Count metrics use count units.

Prometheus appends `_seconds` to duration histograms and `_bytes` to byte histograms; counters append `_total` (a count counter therefore ends in `_total`, without an extra `_count` unit suffix). OTEL puts the unit on the instrument rather than in its metric name. It scales milliseconds to seconds and uses `By` for byte values. For count instruments whose final leaf is plural, it derives a UCUM item annotation from that leaf's singular form: `stream.consumed.messages` uses `{message}`, `kafka.consumer.polls` uses `{poll}`, and `kafka.connects` uses `{connect}`. Nonplural leaves such as `.count` use unit `1`. CloudWatch receives the authored CloudWatch unit. The source inventory below distinguishes a counter from a gauge or histogram: their equal `count` units do not make their measurements interchangeable.

HTTP, RPC, and messaging recommendations share values, but each histogram uses the profile for its measured operation, not the namespace. Fifteen histograms use explicit semantic-family profiles; the remaining 15 have no such profile: 11 count/byte batch histograms and four custom-duration histograms. For those 15, both OpenTelemetry and Prometheus use the standard default boundaries `[0, 5, 10, 25, 50, 75, 100, 250, 500, 750, 1000, 2500, 5000, 7500, 10000]` in exported base units. Thus duration defaults are seconds (their first positive boundary is 5 seconds), while count and byte defaults are counts and bytes; values above 10000 are beyond the final finite boundary. Short custom-duration distributions therefore have poor generic resolution. These defaults are not evidence of workload fit; no custom bounds are inferred.

Historical histogram data is not rebucketed: an older, coarser distribution cannot reconstruct finer percentile detail.

Every framework metric has a registered description. Prometheus and OTEL use that help text; a per-datum `Kind.WithHelp` value overrides the registered description. If no help has been registered for an application-authored metric, the writer falls back to `unit: <unit>`.

## Current framework inventory[​](#current-framework-inventory "Direct link to Current framework inventory")

The V2 inventory contains **80 metrics across 18 namespaces**, including all 30 retained histograms and 16 restored counters.

The dimensions listed are the actual attributes emitted with that metric. Entries in `error.type` or `outcome` describe separate series, not separate metric names. The `kafka.consumer` and `kafka.producer` operation metrics are topic-level (no partition attribute). Franz-go wire-batch metrics and their new volume counters carry `topic.name` and `partition.id`; connection/throttle metrics instead carry `broker.address`. New HTTP response/completion counters include a bounded response class alongside the full numeric code; existing request counters and duration histograms keep their documented dimensions. SQL pool state and SQL open attempts are separate metrics with different semantics.

For `stream.consumed.messages`, `error.type="{{default}}"` counts collected input records before decoding; it is an input-volume total, not an all-processed or successful-record count. A single-message invocation contributes one collected message. A batch contributes its collected record count before decoding, including records later skipped by ignored model lookup, records whose lookup or decoding fails, and records in an empty decoded batch. `error.type="processing_failed"` is an overlapping per-record subset for non-canceled processing errors. For a batch callback error it counts decoded records with false or missing acknowledgements, not the whole collected batch. A false or missing acknowledgement with a nil callback error can request deferred processing or retry without emitting `processing_failed`. Every `GetModel` failure also emits `error.type="model_lookup_failed"`, including ignored failures; only non-ignored lookup failures overlap `processing_failed`. Both diagnostics overlap the collected total. Select `processing_failed` for processing-error counts rather than summing nondefault values. For retry-operation totals, select `error.type="{{default}}"`; `retry_handler_put_failed` is an overlapping failed-put subset, not an additional attempt. The default marker is writer-specific: select `error_type=""` in Prometheus, an absent `error.type` attribute in OpenTelemetry, or the series without that dimension in CloudWatch.

## Folded outcomes and removed names[​](#folded-outcomes-and-removed-names "Direct link to Folded outcomes and removed names")

The V2 contract records operation outcomes as dimensions instead of separate outcome metrics. Re-key queries that used these removed names:

| Removed metric name(s)                                                     | Current metric                                                  | Dimension(s)                                                                                                                                                         |
| -------------------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `stream.errors`                                                            | `stream.consumed.messages`                                      | `error.type`                                                                                                                                                         |
| `kafka.producer.send.errors`                                               | `kafka.producer.sent.messages`                                  | `error.type`                                                                                                                                                         |
| `cloud.aws.kinesis.send.errors`                                            | `cloud.aws.kinesis.sent.messages`                               | `error.type` (generated per-attempt ErrorCode-count summary, e.g. `<count> <ErrorCode> errors`; it may combine codes)                                                |
| `cloud.aws.kinesis.consume.errors`                                         | `cloud.aws.kinesis.consumed.messages`                           | `error.type`                                                                                                                                                         |
| `kvstore.hits`                                                             | `kvstore.reads`                                                 | `hit` (`true`, `false`)                                                                                                                                              |
| `limit.releases`, `limit.throttles`, `limit.errors`                        | `limit.attempted.takes`, `limit.takes`, `limit.throttled.takes` | `attempted.takes` records take starts; terminal `takes` uses only `outcome="allowed"` or `"error"`; throttles use their separate counter. Do not sum these Counters. |
| `mdlsub.consumed.events`, `mdlsub.skipped.events`, `mdlsub.consume.errors` | `mdlsub.events`                                                 | `outcome` (`applied`, `skipped`) and `error.type`                                                                                                                    |
| `kafka.consumer.consume.errors`                                            | `kafka.consumer.consumed.messages`                              | `error.type`                                                                                                                                                         |
| `db.repo.model_event.notify.errors`                                        | `db.repo.model_event.notifications`                             | `error.type`; the former error-only metric is not emitted and there is no `success` label                                                                            |

For disjoint outcomes, sum only exclusive values within the same metric and event boundary. The limiter's start, terminal, and throttle Counters are separate and must not be combined. For `stream.consumed.messages`, `{{default}}` is the all-collected input total, not an all-processed total; `processing_failed` is an overlapping per-record subset of non-canceled processing errors. Every stream `GetModel` failure emits `model_lookup_failed`; only non-ignored lookup failures overlap `processing_failed`. For Kinesis `consumed.messages`, `{{default}}` is the all-processed completed GetRecords-batch total, including handler failures, and `processing_failed` is an overlapping per-record subset. A processing/checkpoint operation error suppresses both the default total and `process.duration`; a per-record handler failure still emits `processing_failed` and checkpoints that record. Kinesis retries use the stream retry path, not selective native Kinesis retry. Kinesis `sent.messages` and `batch.records` are emitted only after a normal `PutRecords` response; request-level API errors produce neither. Failed-record `sent.messages` values are generated per-attempt ErrorCode-count summaries, such as `<count> <ErrorCode> errors`, and may combine codes. For retry operations, filter `error.type="{{default}}"` for attempt totals; `retry_handler_put_failed` is a diagnostic subset. Never add or subtract overlapping series to infer success. `error.type` is a bounded action/reason such as `send_failed`, `connect_failed`, `request_failed`, `request_canceled`, `operation_failed`, `notify_failed`, `apply_failed`, or `processing_failed`, not a Go error type or message. See the [Kinesis shard-reader projection contract](/docs/pr-11/reference/package-cloud_aws_kinesis-reader/.md#cloudwatch-stream-projections) for its stream-level CloudWatch series.
