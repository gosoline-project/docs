Metric schema

This page is the contract for metrics authored by Gosoline. The canonical names, instrument types, authored units, dimensions, and descriptions below describe what the emitters actually record; they are not a copy of OpenTelemetry's metric inventory. Gosoline follows OpenTelemetry semantic conventions for metric grammar, units, and attribute shape where useful, but emits its own names. For example, http.server.request.duration is authored by Gosoline and exported by OTEL as gosoline.http.server.request.duration, not as an unqualified semantic-convention metric.

Source status: The histogram profiles and HTTP server rejection projection described here are coordinated v2 development-source changes under review in Gosoline PR #1434 and HTTPServer PR #11. Existing published pseudo-version pins remain unchanged and do not yet include these follow-ups; this page is not a release or deployment claim.

Schema version​

The current metric contract is v2.0 (metric.SchemaVersion). When the metric daemon is enabled, Gosoline publishes that value as metadata under metric.schema_version. Removing or renaming an authored metric name, dimension key, or unit representation is a breaking change; purely additive metric changes are minor. The current V2 release is the single migration from V1 and emits no dual versions. A new build's schema version does not automatically migrate dashboards, alerts, queries, or autoscaling policies.

Authored names and writer output​

A Gosoline metric is authored as a canonical namespace and leaf, joined with a dot—for example, http.server + request.duration becomes http.server.request.duration. The namespace identifies the emitting subsystem; it is not the application identity. A namespace-less application metric instead uses its leaf as its complete authored name.

Each writer renders that canonical name for its backend:

The first row's duration is authored in milliseconds; Prometheus and OTEL values are scaled to seconds, and both names show the seconds base unit. The Prometheus histogram exposition adds its normal sample suffixes to the base name. Prometheus dimension keys also replace dots with underscores, so the HTTP request.method, route, and response.status_code attributes become request_method, route, and response_status_code labels. The default-dimension marker {{default}} is rendered as an empty Prometheus label value.

For Gosoline metrics, the Prometheus writer always uses the fixed gosoline prefix. It names the framework that authored the metric, not the application. Do not configure an application-specific Prometheus prefix: metric.writer_settings.prometheus.naming.namespace_pattern and metric.writer_settings.prometheus.naming.namespace_delimiter no longer control metric names. Put application identity on the scrape target through service discovery/target labels; Gosoline does not copy app identity into each metric name.

CloudWatch keeps its separate, still-supported namespace setting:

metric:
  writer_settings:
    cloudwatch:
      naming:
        namespace_pattern: "{app.namespace}-{app.name}"
        namespace_delimiter: "/"

This setting controls the CloudWatch namespace in AWS, not the metric name. CloudWatch metric names are rendered from the authored namespace and leaf as one PascalCased name; it does not add gosoline to the metric name. The datum's metric namespace and the CloudWatch service namespace are separate concepts. Consequently, writing an application-authored metric with an empty Gosoline namespace does not remove the configured CloudWatch namespace: only its metric name is PascalCased from the leaf.

For a namespace-less custom name, CloudWatch converts canonical separators in the leaf too: my.custom.metric becomes MyCustomMetric. Prometheus still applies its fixed gosoline writer prefix, converts dots in the leaf to underscores, and appends the unit/counter suffix (the example is a counter). OTEL normalizes and exports that namespace-less leaf without a gosoline. prefix. These behaviors are intentional; re-key CloudWatch dashboards or alarms using namespace-less custom metrics if they previously depended on the unrendered dotted leaf.

Units and descriptions​

The inventory's unit is the unit the emitter authors. Gosoline durations are generally recorded in milliseconds, and Prometheus and OTEL scale those values to seconds and render the base-unit suffix or instrument unit. cloud.aws.kinesis.acquire.duration is the one duration authored in seconds. Byte histograms are authored in bytes. Count metrics use count units.

Prometheus appends _seconds to duration histograms and _bytes to byte histograms; counters append _total (a count counter therefore ends in _total, without an extra _count unit suffix). OTEL puts the unit on the instrument rather than in its metric name. It scales milliseconds to seconds and uses By for byte values. For count instruments whose final leaf is plural, it derives a UCUM item annotation from that leaf's singular form: stream.consumed.messages uses {message}, kafka.consumer.polls uses {poll}, and kafka.connects uses {connect}. Nonplural leaves such as .count use unit 1. CloudWatch receives the authored CloudWatch unit. The source inventory below distinguishes a counter from a gauge or histogram: their equal count units do not make their measurements interchangeable.

HTTP, RPC, and messaging recommendations currently share values, but each histogram uses the profile for its measured operation, not the namespace. Histograms outside the table have no directly applicable standard boundary recommendation identified and retain generic writer defaults. The OTEL explicit-bucket aggregation default uses [0, 5, 10, 25, 50, 75, 100, 250, 500, 750, 1000, 2500, 5000, 7500, 10000] in exported base units, while Prometheus DefBuckets are [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10] in exported base units (OTEL SDK, Prometheus DefBuckets). Thus count and byte values above 10 have no finite Prometheus bucket, and custom waits below five seconds have poor resolution with the generic OTEL boundaries. These exporter defaults are not evidence of workload fit; do not infer a standard profile for the other metrics.

Every framework metric has a registered description. Prometheus and OTEL use that help text; a per-datum Kind.WithHelp value overrides the registered description. If no help has been registered for an application-authored metric, the writer falls back to unit: <unit>.

Current framework inventory​

The V2 inventory contains 80 metrics across 18 namespaces, including all 30 retained histograms and 16 restored counters.

The dimensions listed are the actual attributes emitted with that metric. Entries in error.type or outcome describe separate series, not separate metric names. The kafka.consumer and kafka.producer operation metrics are topic-level (no partition attribute). Franz-go wire-batch metrics and their new volume counters carry topic.name and partition.id; connection/throttle metrics instead carry broker.address. New HTTP response/completion counters include a bounded response class alongside the full numeric code; existing request counters and duration histograms keep their documented dimensions. SQL pool state and SQL open attempts are separate metrics with different semantics.

http.server​

V1→V2 replaced the legacy aggregate and per-route latency measurements without a response-status dimension with one canonical http.server.request.duration histogram keyed by name, route, request.method, and response.status_code. V2 rejection telemetry retains the detailed raw http.server.rejected.requests Counter keyed by name, route, and request.method. A same-name server-wide KindTotal Count projection supplements that Counter only in CloudWatch, uses {name} alone, and receives a zero-valued default per configured server. OTEL and Prometheus continue to export only the detailed Counter. The statusless request counters keep their existing semantics. The restored response counters add the full numeric response.status_code and bounded response.status_class (1xx through 5xx) only to response-count series; outside HTTP codes 100–599 the class uses {{default}}. These response counters have no zero defaults. The existing duration histogram and detailed rejection Counter retain their definitions.

The default marker for missing code/class or success error.type is writer-specific. In Prometheus, the default is an empty label value, so failed completion volume can be selected with sum(gosoline_http_client_completed_requests_total{response_status_code="", response_status_class="", error_type="request_failed"}) (use request_canceled for cancellations); successful status volume can filter response_status_class="5xx". OpenTelemetry omits default attributes, so select failures by error.type while requiring response.status_code and response.status_class to be absent. CloudWatch omits default dimensions; select HTTP client failure series without the code/class dimensions and with the corresponding error.type.

For the raw http.server.routed.responses counter in CloudWatch Metric Insights, fence the query to its five dimensions with FROM SCHEMA("<CloudWatch namespace>", name, route, "request.method", "response.status_code", "response.status_class"). CloudWatch also stores a second class-projected series under the same metric name, omitting response.status_code; for standard 100–599 statuses its dimensions are name, route, request.method, and response.status_class. OpenTelemetry and Prometheus export only the raw five-dimension Counter, without a second projection. Each observed class adds a CloudWatch time series for each name/route/method combination, so the projection adds per-class metric cost.

For class totals and 5xx alarms, use a standard CloudWatch MetricStat with Stat: Sum for the projected metric and all four projection dimensions, including response.status_class; leave out response.status_code. Filter response.status_class="5xx" to include the whole 500–599 class rather than only 500–504. The separate http.server.responses counter has no class projection.

Limiter start, terminal, and throttle Counters describe separate event boundaries; do not sum them as one outcome set. limit.takes contains only terminal allowed or error outcomes, while a throttle is recorded independently in limit.throttled.takes.

For disjoint outcomes, sum only exclusive values within the same metric and event boundary. The limiter's start, terminal, and throttle Counters are separate and must not be combined. For stream.consumed.messages and cloud.aws.kinesis.consumed.messages, {{default}} is the all-processed total and processing_failed is an overlapping subset. Stream model_lookup_failed diagnostics also overlap the default total; only non-ignored lookup failures overlap processing_failed. On retry operations, filter error.type="{{default}}" for attempt totals; retry_handler_put_failed is a diagnostic subset. Never add or subtract overlapping series to infer success. error.type is a bounded action/reason such as send_failed, connect_failed, request_failed, request_canceled, operation_failed, notify_failed, apply_failed, or processing_failed, not a Go error type or message.
